⚙️ 攻擊鏈技術分析
Step 1
社交工程誘餌
寄送 Email / 檔案 / QR Code，內含釣魚連結
Step 2
點擊觸發
攻擊者後端動態向微軟請求 Device Code
Step 3
假冒登入頁
「Continue to Microsoft」彈出真正的 microsoft.com 裝置登入頁
Step 4
受害者輸入 Code
微軟伺服器完成驗證，含 MFA
Step 5
Token 落入攻擊者
access token / refresh token 直送 C2，繞過 MFA 後續存取
Step 6
帳號接管 → BEC
完整存取 M365 / Outlook，導致 BEC、資料外洩、橫向移動
💡 核心論點
●
MFA 在此攻擊鏈中完全無效 受害者是「本人」完成微軟驗證流程，MFA 通過後攻擊者拿到的是合法 token；後續直接帶 token 呼叫 Graph API，不會再觸發任何 MFA。Proofpoint 確認
●
On-Demand 動態產生 = 過期窗口失效 舊版攻擊者得在 15 分鐘內讓受害者上鉤，新版改成「使用者點擊瞬間才向微軟要 code」，每次點擊都是全新的 fresh code，社交工程節奏壓力消失。Proofpoint 確認
●
EvilTokens 疑為 vibe-coded（AI 生成代碼） Proofpoint 研究人員判斷 EvilTokens 平台是以「vibe coding」AI 生成技術建立與維護；iThome 原文未揭露 Proofpoint 的具體推論依據。聲稱未獨立驗證
●
Portal Browser 是 BEC 規模化的關鍵加購 EvilTokens 的 affiliate 可加購 Portal Browser，用於同時存取與管理多個被駭 M365 帳號 — 把單一 token 竊取轉換為「跨組織自動化 BEC 工廠」。Proofpoint / The Hacker News 確認
●
絕大多數鎖定 M365，少部份鎖定 Google iThome 原文與 Proofpoint 觀察一致：M365 是主目標，Google Workspace 為次目標。Adobe / DocuSign 模板主要作為釣魚誘餌而非最終目標。

💻 程式碼範例

使用 Microsoft Graph PowerShell SDK 建立 Report-only 封鎖政策骨架（需依環境補上必要欄位）：

# 連線 Graph，需 Policy.ReadWrite.ConditionalAccess scope Connect-MgGraph -Scopes "Policy.ReadWrite.ConditionalAccess" # 建立封鎖 Device Code Flow 的 CA policy（Report-only） $params = @{ displayName = "Block Device Code Flow (Report-only)" state = "enabledForReportingButNotEnforced" conditions = @{ users = @{ includeUsers = @("All") } applications = @{ includeApplications = @("All") } authenticationFlows = @{ transferMethods = "deviceCodeFlow" } } grantControls = @{ operator = "OR" builtInControls = @("block") } } New-MgIdentityConditionalAccessPolicy -BodyParameter $params

觀察 1–2 週 Report-only 結果無誤後，將 state 改為 enabled。

🎯 結論與行動建議

立即（本週內）

①
於 Entra Conditional Access 建立 Block Device Code Flow 政策 Microsoft 官方建議「盡可能全域封鎖」。建立流程：Conditional Access → Conditions → Authentication flows → 勾選 Device code flow → Grant → Block access。先以 Report-only 跑 1–2 週確認無合法業務被擋，再切 On。

短期（兩週內）

②
建立白名單例外（若無法全域封鎖） 合法 Device Code Flow 使用情境通常只剩：CLI 工具（az login、az ad signed-in-user）、會議室 / 共享裝置、舊式無鍵盤裝置。可用 Conditional Access 例外允許「特定使用者群組 + 特定 IP 範圍 + Compliant Device」三條件交集。
③
監控 Sign-in Logs 中 authenticationProtocol = deviceCode 在 Entra Sign-in Logs 建立查詢與告警；結合 Defender for Cloud Apps / Sentinel 偵測「Device Code 成功登入 → 立即建立 mailbox rule / OAuth grant / 異地 Graph API 大量讀信」異常鏈。

中期（一個月內）

④
使用者教育 對全公司宣導：「任何要你『輸入此代碼到微軟頁面』的 Email / QR / 連結 = 釣魚」。網址正確（microsoft.com）不代表動作安全，重點是「為什麼此時要輸入這個代碼」。
⑤
盤點所有發給 token 的 OAuth App 執行 Entra → Enterprise Applications 審計，列出非預期或低使用率的 OAuth 應用程式，撤銷不需要的 Application 同意；對高風險帳號啟用 token lifetime 縮短（從 90 天降到 7 天）。
