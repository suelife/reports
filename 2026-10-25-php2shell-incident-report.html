⚙️ 技術原理（白話版）與 CVE 比較

白話原理

像櫃台收件：PHP 收到一張超大或層層巢狀的表單，記憶體不夠，做到一半停了。但清理人員以為每張單都填完，照單處理，把「沒填完的半張單」當真。攻擊者事先把那塊記憶體塞好內容，清理時 PHP 就被誘導去執行系統指令（CVE-2026-109618）。

上一個請求的殘影：同一個 PHP 工作行程（worker）處理完一個失敗請求後，仍留著指向「已釋放記憶體」的指標；下一個請求拿來用，就能被操控（CVE-2026-109619）。

為什麼擋不住：這些事發生在 PHP 解析請求的階段，網站程式碼（含登入檢查）還沒開始跑，所以任何 PHP 應用程式，連只印一行字的頁面都可能中招。攻擊者還得突破記憶體位址隨機化（ASLR）；Wiz 與 Datadog 指出可借 PHPSESSID cookie 洩漏記憶體，降低難度。

步驟 1
送特製表單
multipart 上傳，或層層巢狀的超長欄位名
步驟 2
記憶體超限
PHP 在請求初始化中途中斷
步驟 3
殘留半成品
內部資料只做一半，或指標指向已釋放記憶體
步驟 4
清理誤信
收尾或下個請求把殘留當有效資料
步驟 5
執行指令
worker 權限下啟動 shell（如 www-data）

官方修補的做法：記憶體「軟上限」改為延後到安全點才報錯；超過「硬上限」就直接結束該 worker（_exit(137)），不再跑清理；並在收尾時重設請求相關的全域狀態（Datadog 分析）。Datadog 提醒同類模式（先更新計數、後配置記憶體）可能還有其他變體。

💡 風險判斷
1
▲ 未修補的對外 PHP，風險高。 免認證、應用程式碼之前觸發、PHP 約占 70% 的網站。Palo Alto Xpanse 估計有 2,260 萬個對外實例可能受影響；Qualys 估計約 71% 的 PHP 實例跑 5.4 至 8.1（已停止維護），多數不會再有官方修補。
2
◆ 「大規模成功入侵」目前證據有限，但不能當成安全。 多數公開 PoC 是無法 RCE 的 vibe-coded 版本（Mandiant），攻擊者實測的 11 個目標無一符合其工具條件（SOCRadar）。但 VulnCheck 已有可繞過 ASLR 的 exploit（僅供付費客戶），Mandiant 驗證過部分 PoC 可對預設 mod_php 成功，Unit 42 也記錄到一起後滲透。
3
◆ 時間窗以小時計。 揭露前就有嘗試，修補後數小時內出現 PoC；AWS 建議關鍵漏洞的修補與緩解以小時計、調查從 10-17 起算。Wiz 認為 AI 讓「把複雜漏洞變成可用 exploit」的門檻大降；Calif 則強調這次主要靠研究者對 PHP 歷史的熟悉，AI 是輔助。

偵測指標

沒有任何單一訊號能下定論，請交叉比對；成功的利用不一定讓 worker 當掉，HTTP 狀態也可能是 200（Datadog）。

層次要找什麼
請求（WAF、反向代理、存取紀錄）你的應用平常不用的 PHP_SESSION_UPLOAD_PROGRESS 欄位；一個請求內數百個 multipart 區段、或 files[R00001][a][a] 式的深層巢狀欄位名；數 MB 的單一欄位名；檔名含 <?php 或 |O:；宣告很大 Content-Length 卻慢傳或不傳完；回應的 Set-Cookie: PHPSESSID= 異常長、百分比編碼或含二進位內容（可能是記憶體洩漏）
PHP／Apache 錯誤紀錄Allowed memory size ... exhausted 且位置為 Unknown on line 0（代表發生在請求初始化）；Apache AH00052 ... Segmentation fault (11)；短時間內同一 worker 幾次記憶體耗盡後歸於平靜；重複 HTTP 500、worker 異常重啟
主機處理程序php-fpm、php-cgi、httpd／apache2、lsphp、frankenphp 的子行程出現 sh、bash、cmd、powershell、python、perl；curl、wget、nc、/dev/tcp/、mkfifo；whoami、id、uname 偵察；網站目錄新增 PHP 檔、新排程或新帳號
代理式攻擊特徵Unit 42 記錄到指令批次以 ==SHELLUSER==、==PASSWD== 之類分隔字樣包起來，利於 AI 解析輸出；任務短而連續、失敗後快速換招
回查起點與現成規則從 2026-10-17 起查（AWS），不是從 10-21；CISA 提供 SIGMA 規則；Datadog、Unit 42、Wiz、Palo Alto 各有偵測；AWS 公布 6 個觀測 IP（含共用匿名基礎設施，建議調查而非直接封鎖）

產品與平台因應

  • WordPress：WordPress.org 稱不需、也不會出 WordPress 更新，要更新的是 PHP；自管主機無法升級者應考慮下線。
  • Drupal：安全團隊 PSA-2026-10-20 事前預告 10-21 的 PHP 更新，建議自行更新 PHP 或依主機商指示（僅讀到搜尋摘要）。
  • Laravel：Laravel Cloud 已就地修補；Forge 需逐台按「Update PHP」（支援 5.6 至 8.5，Ubuntu 20.04 以下無法更新，建議新建主機）；Vapor 需重新部署；PHP 8.0／8.1 無修補。
  • Magento：Calif 已在 Magento 2.4.9 測試環境確認免認證 RCE；Adobe 官方公告我未查到（未證實）。二手整理稱 Magento 2.4.4／2.4.5 只支援 PHP 8.1，沒有官方修補版，需取得廠商回補或升級。
  • 內嵌 PHP 的設備：Palo Alto PAN-OS 僅管理介面受影響（GlobalProtect 與 Captive Portal 不受影響），hotfix 10-27 至 10-30 陸續釋出，期間應限制管理介面只對內網；QNAP、Cisco（Expressway、URWB）、Synology 也有公告（僅讀到搜尋摘要，未逐一核對）。
  • 雲端與 CDN：Vercel 於揭露前部署 WAF，但仍要求升級 PHP；Cloudflare、AWS、Google Cloud 同樣提供規則，皆強調不能取代修補。

  • 國家資通安全研究院（NICS）：已發布警訊（頁面內容我讀不到，僅確認標題存在）。
⚖️ 爭議與未解問題
  • 是否已有成功入侵：Unit 42 稱觀測到歐洲政府單位被入侵，兩小時內取得密碼雜湊與 MFA 密鑰，並嘗試取得網域管理員；但 Unit 42 頁面沒有明講此案是經由哪個 CVE 進入。NCSC-NL（10-23）稱有一則境外通報、尚未證實成功。TechCrunch（10-24）說 Palo Alto 與 Trail of Bits 都確認了入侵，我查不到 Trail of Bits 的公開說法（未證實）。
  • 揭露前的利用從何而來：AWS 看到 10-17 的嘗試，不清楚對方怎麼取得資訊。可能是洩漏、獨立發現，或其他，皆無證據（未證實）。
  • CVE 與漏洞的對應各家不一：PHP 官方把 109618 定義為 OOM 損毀、109619 為殘留全域狀態；Wiz 把 upload-progress 反序列化 UAF 與記憶體洩漏歸在 109618，把 fatal 回溯與 OPcache 型別混淆歸在 109619；Datadog 則把 upload progress 路徑歸在 109619。本文以官方分類為準。
  • 曝險規模差距很大：VulnCheck 約 260 萬台對外主機；Palo Alto 2,260 萬實例；Censys 約 3,440 萬服務（以版本號判斷，忽略發行版回補）；Qualys 約 1.1 億實例、71% 為 EOL。計算方式不同，只能說量非常大。
  • CVE-2026-115560 的修補日期與完整影響：未公布，官方稱下個例行版本；NCSC-NL 與 PHP 都認為難以達成 RCE，但尚無完整公告。
  • 是否會進 CISA KEV：目前未收錄，隨時可能變動。
  • 其他變體：Wiz 與 Datadog 都認為同一類缺陷還有其他實例；官方補丁號稱從根本處理，是否完全涵蓋有待觀察。
  • 台灣實際受影響政府網站數與修補進度：資安署只公布「約 200 個使用 PHP」，未公布實際受影響數與進度。另外我找不到名為「TWNCERT」的單位或其通報，台灣的對應單位是資安署、NICS、TWCERT/CC、N-ISAC。
  • 時間細節的出入：資安署發警訊的時間，iThome 寫「1 小時內」，中央社與聯合報寫「3 小時內」；本文未採用其中任一數字。
🎯 結論與行動建議（企業該做什麼）
▲
立即（今天，以小時計）
  • 盤點實際對外服務的 PHP：看的是跑網站的 php-fpm、mod_php、容器與廠商設備內建 PHP，不是只看命令列的 php -v。優先處理對外、Apache mod_php。
  • 升級並重啟：升到 8.5.12、8.4.27、8.3.36、8.2.35，或確認發行版套件含兩個 CVE 的修補；重啟 php-fpm／Apache，容器重建映像；再次確認「執行中」的版本與 worker 啟動時間。
  • 全域關閉 upload progress：在 php.ini 或 FPM pool 設 session.upload_progress.enabled=0 並重啟；升級後也保留，直到下個例行版本。確認 display_errors=Off。
  • 無法立即升級的對外系統：國際機關建議隔離或下線；若選擇留線，至少上 WAF（block 模式）、限制請求大小，並限縮來源 IP。
  • 從 10-17 起回查紀錄：用上一節的偵測指標，重點看 web worker 衍生 shell、網站目錄新增 PHP 檔。
◆
本週
  • 舊版本處置：PHP 7.4／8.0／8.1 取廠商回補，或用官方最小原始碼修補，測試後上線；7.3 以下無修補，移出網際網路，只開 VPN 或內網。
  • 委外與代管業者書面確認：跑的是哪個 PHP 版本與 SAPI、修補證據、worker 重啟時間、同帳號下其他 pool 與測試站是否涵蓋。
  • 內嵌 PHP 的設備：PAN-OS 等待 10-27 至 10-30 的 hotfix 期間，管理介面限內網；追蹤 QNAP、Cisco、Synology 等供應商公告。
  • 建立偵測：對 web server 或 PHP 行程衍生 shell、下載工具設告警；匯入 CISA SIGMA 規則。
  • 若有入侵跡象：先隔離並保留紀錄，不要急著重灌；輪換該主機上的密碼、API 金鑰與憑證（Wiz 指出記憶體洩漏可能含這些）；通報 TWCERT/CC（int_report@cert.org.tw）或資安署。
●
後續（本月起）
  • 追蹤下個 PHP 例行版本：修補 CVE-2026-115560；在那之前保持 upload progress 關閉。
  • 規劃升級：PHP 8.2 於 2026-12-31 結束支援，8.1 以下立即排期汰換。
  • 修補 SLA 改以小時計：對外關鍵漏洞不再用 7 天或 30 天的窗口（AWS 建議）。
  • 建立含內嵌 PHP 的資產清冊：CISA 與 NCSC-UK 都提醒 PHP 常是其他軟體的元件，不易從外部看出。
  • 架構考量（本研析建議，非官方）：評估由 mod_php 遷到 PHP-FPM 並加上隔離，因為官方與 Mandiant 都指出 mod_php 風險最高。
