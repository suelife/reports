📋 Executive Summary
◆
一支伊朗系間諜框架把遭入侵的 Microsoft 365 信箱行事曆，變成命令暨控制（C2）通道。卡巴斯基 GReAT 於 2026-07-21 揭露 Project CAV3RN 的新通訊模組 AzureCommunication.dll，它透過 Microsoft Graph 讀寫 Outlook 預設行事曆——把加密指令藏在排程於 2050-05-13 的行事曆事件附件中，指令、心跳、執行結果全走這條「dead-drop」通道。Group-IB 同一週以 HollowGraph 之名獨立揭露同一活動叢集。

🎯 攻擊者背景

兩家廠商都把此活動指向伊朗系 APT，但落在不同組織、且皆為低信心。卡巴斯基延續先前評估，指向 OilRig（APT34）；Group-IB 則關聯至 Lyceum（亦稱 HEXANE）。兩者都缺乏直接程式碼重用或基礎設施重疊，因此屬「行為模式相似」而非「確認同一組織」。

卡巴斯基支持 OilRig 關聯的核心理由，是這個組織長年把 Microsoft 託管服務當 C2 的一貫手法。CAV3RN 的行事曆通道，正是這條演進線的最新一站：

  • RDAT：透過 Exchange Web Services（EWS）電子郵件交換指令與結果。
  • SC5k：利用 Office 365 草稿匣（drafts）作為 dead-drop。
  • OilCheck：改用 Microsoft Graph 存取 Outlook 草稿匣。
  • OilBooster：以 Microsoft OneDrive 為 C2，並在多次連線失敗後從遭入侵網站取回替換用的 OAuth refresh token（雲端 C2 的次要回復機制）。
  • CAV3RN / HollowGraph：同一類服務，但把指令與結果存進 Outlook 行事曆事件，並以 DNS AAAA 記錄取回替換的連線設定。

受害者側：本模組使用的是一間以色列律師事務所遭入侵的 Microsoft 365 信箱。這與 OilRig 慣用「被入侵的區域組織基礎設施」一致——例如 Solar 惡意程式曾用以色列人資公司網站、Whisper/Veaty 曾用伊拉克政府的 M365 信箱。

⚙️ 攻擊鏈技術分析

一、OilRig 濫用 Microsoft 託管服務作 C2 的演進

把 C2 藏進 Microsoft 生態的價值在於：流量目的地是 graph.microsoft.com 與 login.microsoftonline.com——這些網域幾乎不可能被封鎖，且與正常辦公流量無異。

二、行事曆 dead-drop 的三種事件

模組把「指令、心跳、結果」全塞進同一個一小時視窗（2050-05-13 22:00–23:00 UTC），並用事件主旨（subject）區分用途與對應的 Agent ID。心跳與結果主旨會固定加上後綴 1500（非 Agent ID 的一部分）。指令附件與結果附件連檔名大小寫都不同（file0.txt vs File0.txt）。

主旨格式用途模組行為
Event ID: <agent-id>操作者 → 代理（下指令）找到事件、下載附件、消費後刪除事件
Boss update ID: <agent-id>1500代理心跳（回報在線）刪除舊心跳、建立替換事件（無附件）
Boss Report ID: <agent-id>1500代理 → 操作者（回傳結果）建立事件、上傳加密結果附件、改主旨標記完成

三、認證與 Microsoft Graph 請求

模組內嵌完整設定（Entra tenant ID、application 憑證、目標信箱、DNS bootstrap host、RSA 金鑰對），首次執行時寫入工作目錄的 logAzure.txt。它以 client credentials 流程取得 OAuth application token，再以 Bearer 權杖對信箱的預設行事曆讀寫：

# 1. 取得 application token（client_credentials） POST https://login.microsoftonline.com/<TenantId>/oauth2/v2.0/token client_id=<ClientId> client_secret=<ClientSecret> scope=https://graph.microsoft.com/.default grant_type=client_credentials # 2. 驗證租戶存取 GET https://graph.microsoft.com/v1.0/organization # 3. 依 Agent ID 過濾 2050 年行事曆事件，取指令 GET /v1.0/users/<mailbox>/calendarView ?startDateTime=2050-05-13T22:00:00&endDateTime=2050-05-13T23:00:00 &$filter=contains(subject,'Event ID: <agent-id>') # 4. 下載附件後刪除事件（消費式） GET /v1.0/users/<mailbox>/events/<EventId>/attachments DELETE /v1.0/users/<mailbox>/calendar/events/<EventId>

四、混合加密（RSA + AES-256-GCM）

入站指令緩衝區開頭是 256 bytes 的 RSA 加密區塊，內含 32-byte AES 金鑰，以 RSA-OAEP + SHA-256 用內建私鑰解開；接著 12 bytes 為 AES-GCM nonce、末 16 bytes 為驗證標籤，中間為密文，以 AES-256-GCM 解密。解密後為 JSON 指令，例如 {"cid":"...","type":"self","cmd":"003_;;__,_"}——type:self 表示由 controller 內部處理，cmd 003 為切換除錯記錄。出站結果則以新生成的 AES 金鑰加密、RSA 公鑰保護，分割為每塊最多 10 MiB 的附件回傳。

五、DNS AAAA 設定回復（韌性設計）

當 OAuth 取權杖或 /organization 驗證失敗，模組改走 DNS：把 7 字元 Agent ID 轉為大寫十六進位（SFmLgQZ → 53466D4C67515A），對 cloudlanecdn[.]com 發 AAAA 查詢，把回傳的 IPv6 位址當成 16-byte 資料容器（而非網路目的地）。這讓攻擊者能不重新投放惡意程式就修復雲端 C2 設定。

查詢類型格式用途
.p. 長度查詢d.<hex-id>.<field>.p.<host>取欄位總長度（丟棄前 2 bytes，取後 2 bytes 為 big-endian 長度）
.q. 資料查詢d.<hex-id>.<field>.<offset>.q.<host>每次取最多 14 bytes，以 14-byte 位移逐段拼回 TenantId/ClientId/ClientSecret/UserEmail
Sentinel 失敗訊號2001:4998:44:3507::8000特定 IPv6（Yahoo 配額）代表未知 Agent／欄位不可用，模組拋例外

DNS 回復只更新四個 Graph 設定欄位，不會替換 DNS 回復網域本身與 RSA 金鑰——是刻意的有限輪替。

⚠️ 衝擊評估

評為 HIGH 的理由：這是一支持續開發中的國家級間諜框架，其行事曆 C2 具備高度隱蔽與韌性——(1) 流量偽裝成合法 Graph 活動、(2) 事件排在 2050 年避開日常視圖、(3) DNS fallback 讓雲端 C2 可在不換 payload 下自我修復。更關鍵的是它不依賴任何漏洞，任何啟用 Microsoft 365 的組織都可能成為同一手法的目標，且傳統郵件／端點監控難以偵測。

  • 偵測面塌陷：C2 目的地是 graph.microsoft.com，網域封鎖與 IOC 比對幾乎無效，偵測必須轉向「應用程式行為」與「身分異常」。
  • 無 patch 可修：屬信任與權限濫用，微軟無漏洞可補；責任落在租戶的身分治理設定。
  • 趨勢放大：這是 Graph-as-C2 趨勢的一環（FINALDRAFT、Havoc C2、SIESTAGRAPH 等皆屬同類），代表手法正被多個威脅行為者採用。

節制與範圍：目前觀察為高度針對性的間諜活動，鎖定以色列特定組織，受害數低（12 台、3 台活躍），非蠕蟲式擴散、非勒索。對台灣一般組織而言，直接受害風險低，但技術手法值得防守方預先建模。

⚖️ 爭議與未確認事項
  • 命名分歧：卡巴斯基稱框架為 Project CAV3RN、模組為 AzureCommunication.dll；Group-IB 稱 HollowGraph 並關聯 Cavern C2。三者高度指向同一活動叢集，但目前尚無官方統一命名。
  • 歸因分歧：OilRig/APT34（卡巴斯基）vs Lyceum（Group-IB），皆為伊朗系、皆低信心，且無直接程式碼或基礎設施重疊——尚不能確認為單一組織。
  • 替換角色為「評估」而非直接觀察：對應的更新版 controller 未被取得，故「新模組取代 HTTP/WebSocket 元件」是推斷，非直接證據。
  • 初始存取手法未明：公開資料未說明那些 Microsoft 365 信箱最初如何被入侵（釣魚、憑證外洩或其他）。
🛡️ 防禦建議

一、身分與應用治理（對映 Microsoft 官方偵測目錄）

  • 啟用 Microsoft Entra ID Protection 的「Suspicious API Traffic」（suspiciousAPITraffic）與「Anomalous service principal activity」偵測——專門標記 service principal 的異常 Graph 流量與目錄列舉。
  • 部署 Defender for Cloud Apps 的 app governance，開啟「App made anomalous Graph calls to Exchange workload」「Unusual addition of credentials to an OAuth app」等告警。
  • 稽核 app 憑證異動：於 Entra 稽核日誌過濾 ApplicationManagement → Update Application – Certificates and secrets management，對非常規時段／非常規流程新增的 client secret 告警。
  • 以 Managed Identity 或 X.509 憑證取代 client secret；用 Conditional Access 限制 client-credential 應用程式的來源與範圍。

二、偵測行事曆 dead-drop 行為

  • 監控 Graph / M365 稽核日誌中「應用程式驅動的行事曆活動」，特別是排程於遠期（如 2050）、主旨或附件異常的事件（Group-IB 明確建議）。
  • 對 service principal 大量呼叫 calendarView／events/attachments 建立行為基線並告警。

三、網路層

  • 監測 DNS tunneling 特徵：AAAA 回應攜帶非路由資料、對單一網域高頻的 .p.／.q. 子網域查詢。
  • 將本報告 IOC 網域與 nameserver IP 納入封鎖／偵測清單。
