OpenSSH *sshole（CVE-2026-123158）
musl 上超長密碼可登入「無密碼／僅金鑰」帳號

公告日期　2026-11-05（台北） 報告日期　2026-11-06 受影響元件　OpenSSH sshd（musl libc、未啟用 PAM） 發現者　Özgün Kültekin（Wakefield） 撰寫人　grok
📋 Executive Summary
◆
一句話重點： 在使用 musl libc、且 sshd 未走 PAM 的 Linux（典型為 Alpine）上，若仍開啟密碼登入，攻擊者只要對 /etc/shadow 密碼欄為 * 的帳號送出約 257 至 1024 bytes 的超長密碼，即可一次登入成功；不需知道任何真實密碼。
◆
結論： OpenSSH 評為 Critical 並於 2026-11-05 釋出 10.6p2 緩解；MITRE 已登錄 CVE-2026-123158（CVSS 3.1 基礎分 8.1 High）。Alpine 已對 3.16 至 edge 各分支回移植。glibc 發行版（Debian／Ubuntu／Fedora）與啟用 PAM 的 sshd 不受影響。公開來源未確認在野利用。
!
這跟我們有沒有關係： 一般 Debian／Ubuntu 伺服器（glibc＋預設 PAM）通常不在範圍內。需盤點：Alpine 容器／主機若有跑 sshd、OpenWrt／Buildroot／Yocto 自建 OpenSSH、雲端 tiny-cloud 映像的 alpine 帳號（搭配 passwordless doas 可升 root）。詳見「偵測與緩解」與「台灣相關性」。

🔬 技術細節

預期行為： 帳號在 /etc/shadow 密碼欄放 * 表示「不接受任何密碼」（常見於僅金鑰登入、或 Alpine 預設 root）。鎖定帳號則用 !。

破口組合： 無 PAM 的 sshd 自行呼叫 C 函式庫 crypt()。對欄位太短、沒有 salt 的帳號，sshd 會借用另一個有真實雜湊帳號的 salt（避免時序洩漏使用者名稱）。musl 在密碼過長時讓 crypt() 失敗並回傳字面 *；存放欄位也是 *，字串相等即登入成功。有真實雜湊的帳號本身不會被這條路徑繞過。

為何要有「另一個真實雜湊」： Alpine 說明一台機器上只要有一個 $5$／$6$ 密碼，就足以讓所有 * 帳號變得可被這條路徑登入。

修復思路： OpenSSH 10.6p2 在 sshd 端拒絕把「過短、不可能是真實雜湊」的存放欄位當成匹配成功（commit 4353fdc4）。OpenSSH 團隊認為根因在 musl／組態組合，但仍以 Critical 速度出 workaround。

CVSS 解讀： AC:H 反映需同時滿足 musl、無 PAM、開密碼登入、有 * 帳號與真實雜湊等多條件；一旦成立則遠端、無須權限與使用者互動即可取得帳號存取（C／I／A 皆 High）。

本報告不提供利用步驟或 PoC。

🛡️ 偵測與緩解

1. 先判斷自己是不是 musl＋OpenSSH：

# 是否 musl
ldd --version 2>&1 | head -1
# 或
apk --version 2>/dev/null

# 有效 sshd 設定（密碼登入／PAM）
sshd -T 2>/dev/null | grep -iE 'passwordauthentication|usepam'

# openssh 版本
sshd -V 2>&1 | head -1
apk info openssh 2>/dev/null

2. Alpine 升級並重啟（只升級不夠）：

apk upgrade -U -a
rc-service sshd restart
# 確認有效設定
sshd -T | grep -i passwordauthentication

3. 無法立即升級時的暫時緩解（先確認金鑰登入可用，並保留現有工作階段）：

mkdir -p /etc/ssh/sshd_config.d
echo 'PasswordAuthentication no' > /etc/ssh/sshd_config.d/00-no-passwords.conf
# Alpine 3.19 以前可能忽略 drop-in，請同時改 /etc/ssh/sshd_config
sshd -t && rc-service sshd restart
sshd -T | grep -i passwordauthentication
# 預期：passwordauthentication no

4. 帳號面加固： 不用的帳號改為 ! 鎖定；tiny-cloud 環境檢視並移除 alpine 的 passwordless doas；雲端映像若經 cloud-init 已寫入 PasswordAuthentication no 則不在條件內（Alpine 明列）。

5. 是否可能已遭利用： 檢查日誌是否出現「不應接受密碼的帳號」卻有 Accepted password for：

grep "Accepted password" /var/log/messages
grep -E '^(alpine|root):' /etc/shadow

若 shadow 為 * 但日誌顯示密碼登入成功，應視為可能遭利用：檢視 doas／sudo、新增使用者、authorized_keys 與近期檔案；無法排除則以重建主機為原則（Alpine 建議）。

6. Debian／Ubuntu 主機： 一般無需為此 CVE 緊急升 OpenSSH；仍建議維持金鑰登入、關閉密碼登入作為基線 hardening，但那是通案而非本洞必修項。

🇹🇼 台灣相關性
  • 主流伺服器多半安全： 台灣企業與政府常見的 Debian／Ubuntu／RHEL 系為 glibc，且多啟用 PAM，不落在此利用條件。
  • 要盤點的是「輕量／嵌入式／容器」： 內部 Alpine 基礎映像若啟用 sshd、維運用 Alpine 跳板、OpenWrt 家用／分部路由器若改裝 OpenSSH、工控或自研韌體（Buildroot／Yocto）若連結 musl＋OpenSSH。
  • 雲端： 若曾用 Alpine 官方 tiny-cloud AMI／VHD，且之後設定過主控台密碼或 user-data 寫入雜湊密碼，alpine＋doas 組合風險升高；應確認映像點修版或已關密碼登入。
  • 資安產品與邊界設備： 許多網路設備用 Dropbear 而非 OpenSSH；不能假設「有 SSH 就中招」，要以實際二進位與 libc 為準。
  • 優先順序建議： ① 對外暴露 SSH 的 Alpine／musl 主機 ② 雲端 tiny-cloud 實例 ③ 內網跳板與 CI runner 上的 Alpine sshd ④ OpenWrt／自建韌體清冊。
🧭 結構性觀察
  • 錯誤碼與「停用」記號撞車： musl 用 * 表示 crypt 失敗，Unix 傳統又用 * 表示無密碼；兩個各自合理的選擇疊在一起才爆。
  • 時序防護的附帶成本： CVE-2016-6210 的修法讓「本來不該雜湊」的帳號也走 crypt，擴大了與 musl 行為互動的攻擊面。
  • 「升套件 ≠ 生效」： Alpine 特別強調必須重啟 sshd；資安通報若只寫「請更新」而漏重啟，線上仍跑舊 daemon。
  • AI 輔助發現加速公開： OpenSSH 釋出說明坦言近期大量 AI／AI 輔助回報，並改為更頻繁發版；本洞亦據媒體稱以 AI 代理大量 fuzz 登入路徑發現。
